# Research dossier — per-project observability contracts

## Question

What exactly is the current observability validation behavior — the enums,
checks, inline literals, and call sites — that Phase 0 must pin and Phase 1
must extract, and are the approved spec's factual claims about the engine
accurate?

## Sources

All claims below were verified live on 2026-08-30 by reading the running
engine source in this session. No web sources were needed or used; the
subject is this repo's own code.

- `scripts/operating-layer.py` at HEAD `e9e0518` (11,581 lines)
- `scripts/tests/operating_layer_test.py` (137-check suite)
- `.planning/2026-08-30-per-project-observability-contracts.md` (approved spec)

## Verified claims (each cited; read this session)

1. **Spec line references are accurate.** `OBSERVABILITY_*` constants span
   `operating-layer.py:1486-1663`. Metric-name-set EQUALITY is enforced at
   `:2049` (artifact) and `:2194` (receipt). Tradebot-only event names are
   enforced at `:1872` (`event_name not in OBSERVABILITY_EVENT_NAMES`).
2. **Every metric and event enum is tradebot-specific.** All 7
   `OBSERVABILITY_METRIC_NAMES` begin `tradebot_` (`:1486-1494`); all 19
   `OBSERVABILITY_EVENT_NAMES` begin `tradebot.` (`:1524-1534`).
3. **The fail-closed default is real.**
   `OBSERVABILITY_RUNTIME_VERIFIER_TRUST_STATE =
"TRUSTED_VERIFIER_NOT_CONFIGURED"` (`:1616`) and
   `OBSERVABILITY_TRUSTED_VERIFIER_SHA256 = frozenset()` (`:1617`). The
   observability branch of `proof_is_verified` (`:3275-3306`) refuses credit
   at `:3279-3280` unless the trust state is `CONFIGURED_AND_VERIFIED` AND
   the receipt's `verifier_source_sha256` is in the allowlist. A second
   consumer at `:5152` emits the plain-English refusal reason.
4. **The anti-gaming invariants the spec preserves are all in
   `proof_is_verified` (`:3282-3306`), not in the enums**: 7-field sha256
   map equality, per-artifact canary results all True, restoration-hash
   equality, verifier binding, snapshot stability, outcome `runtime`,
   scope in {runtime, production}. Decision 3 (contract defines WHAT, never
   HOW MUCH) is implementable exactly as written: these checks reference
   `OBSERVABILITY_RECEIPT_ARTIFACT_FIELDS` (shape), never the tradebot
   content enums.
5. **The extraction surface is larger than "metric enums" — 36 module-level
   constants plus inline literals** (count measured by AST parse this
   session, not by eye). Per-project (goes in the contract
   file): metric names/label-values/domains, event names, correlation
   fields + hash/timestamp/sequence subsets, allowed
   assets/modes/risk-decisions/reason-codes, drill incident/trace-name/
   alert, runbook question-ids/evidence-fields/dispositions/answer-codes/
   enum-values/missing-evidence, runbook answer contract (`:1663`), trusted
   verifier sha list. Engine-invariant (stays constant): receipt artifact
   fields, JSON artifact types, runtime-true fields, pre-runtime state,
   context fields, the five MAX_* limits, allowed stages/verdicts.
6. **Inline tradebot literals exist OUTSIDE the constants block and must
   not be missed in Phase 1**: `alert_artifact` validation hardcodes
   `status == "FIRED"` and `safe_action == "HALT_ENTRIES_RECONCILE_ONLY"`
   inline at `:2088-2089` (the same value also sits in
   `OBSERVABILITY_DRILL_ALERT`). `canary_artifact` hardcodes the results
   map `{"disabled_alert"/"missing_signal": "FAILED_AS_EXPECTED"}` at
   `:2123-2127`. The safe_action value is tradebot semantics; the canary
   result keys are arguably generic — Phase 1 must decide each explicitly.
7. **Correlation-field EQUALITY (`:2069`, `:2201`) is a second per-project
   pin** with tradebot-shaped members (`client_order_id`, `risk_decision`,
   `market_event_ts`…) — same class of failure as the metric-name pin the
   spec leads with.
8. **Decision 5's resolution path exists as claimed.** `resolve_project_dir`
   (`:4373`) resolves the work item's project; proof context (work_id,
   recommendation_id, project, target_project) is bound as `expected` into
   receipt validation at `:4505` and `:4877`, and receipts that disagree
   with the caller binding are refused (`:2231-2237`). A receipt cannot
   pick its own context today; the contract lookup must reuse this key.
9. **One call site validates WITHOUT caller binding:**
   `observability_receipt_credit_scope` (`:2270-2272`) calls
   `validate_observability_runtime_receipt(receipt, now=now)` with no
   `expected` and no `artifact_base`. Under per-project contracts this site
   needs the resolved project passed in — it cannot derive one honestly
   from the receipt alone (decision 5 forbids receipt-supplied keys).
10. **Phase 0 can reuse an existing fixture builder — corrected claim.**
    An initial truncated grep suggested the suite never calls the
    validators; a counted re-measure found 24 direct
    `validate_observability_runtime_receipt` calls
    (`operating_layer_test.py:4562-4962`) and a
    `_observability_runtime_fixture` builder (`:4197`) that produces a
    fully VALID receipt — asserted error-free at `:4558-4560`. Phase 0
    therefore extends this fixture with the spec's four synthetic cases
    instead of building from scratch. What characterization still adds:
    the existing checks assert error SUBSTRINGS via `any(...)`; G1 needs
    exact error-LIST goldens so extraction can be proved byte-identical.

## Unknowns, classified

- **warn — credit-scope call site (claim 9):** `observability_receipt_credit_scope`
  has no work-item context. Phase 2 must thread the resolved project into it
  or accept that this helper stays tradebot-defaulted until refactored.
  Not a blocker: the crediting path (`work-log`) has the binding it needs.
- **warn — inline literals (claim 6):** the spec says "every enum in
  OBSERVABILITY_*"; the true surface includes two inline validator literals.
  Phase 1's characterization gate (G1) will catch a miss, but the extractor
  should work from this dossier's claim-5/6 catalog, not from a grep of the
  constants block alone.
- **info — `OBSERVABILITY_PRE_RUNTIME_STATE` (`:1635-1647`):** carries
  tradebot-agnostic status strings; it gates Tier-A blocked receipts
  (`:1773`). Treated as engine-invariant; nothing tradebot-specific inside.
- **info — timestamps/limits:** the five `OBSERVABILITY_MAX_*` limits are
  proof-strength knobs, so per decision 3 they stay engine constants.

## Verdict

The spec is planning-ready as approved. No locked decision is contradicted
by the live code. Two refinements travel forward as carry-forward
constraints: Phase 1 must extract from the claim-5/6 catalog (34 constants
plus 2 inline literal sites), and Phase 2 must handle the unbound call site
in claim 9 without violating decision 5.
